# subagents ガイド

サブエージェントは、独立したコンテキストで動く専門特化のアシスタントです。メインの会話とは別のウィンドウで作業し、結果だけを返します。

CKMS が提供するサブエージェントは `knowledge-curator` の 1 つだけです。数を絞っているのには理由があります。

## なぜ 1 つだけなのか

Cursor の公式ドキュメントは、サブエージェントの多用をアンチパターンとして挙げています。委譲のたびにコンテキストの受け渡しコストがかかり、親エージェントは子の作業過程を見られないため、細かい調整が効かなくなるからです。スキルで足りることをサブエージェントにすると、遅く、不便になります。

サブエージェントが有効なのは、**出力が大きいわりに、必要な結論が小さい**作業です。知識ベースの全走査はこれに当てはまります。判断 50 件・パターン 30 件を読むと数万トークンになりますが、そこから欲しいのは「どれを直すべきか」という数十行のリストだけです。この読み込みをメインの会話でやると、以降の作業でコンテキストが不足します。

記録の追加（`/record-decision` など）は逆です。ユーザーとの往復でヒアリングしながら書くので、別コンテキストに隔離する意味がありません。だからアクションスキルのままにしています。

## knowledge-curator

定義は [agents/knowledge-curator.md](../../agents/knowledge-curator.md) です。

```yaml
---
name: knowledge-curator
description: 知識ベースの棚卸し担当。蓄積された技術判断・実装パターン・改善記録・デバッグセッションを全走査し、陳腐化・矛盾・重複・リンク切れ・記録漏れを報告する。
model: inherit
readonly: true
---
```

`readonly: true` を指定しているため、このサブエージェントはファイルを変更できません。棚卸しは「何を直すべきか」を洗い出す作業であって、直すかどうかはユーザーが決めることだからです。読み取り専用にしておけば、意図しない一括書き換えが起きません。

`model: inherit` は親エージェントと同じモデルを使う指定です。走査の質はモデルに依存するため、ユーザーが選んだモデルをそのまま使います。

### 検出する項目

| 分類 | 内容 |
|------|------|
| 陳腐化 | 現在の技術スタックや方針と矛盾する記録 |
| 矛盾 | 複数のファイルが互いに反する内容を主張している |
| 重複 | 同じ内容が複数ファイルに分散している |
| リンク切れ | Markdown リンクの参照先が存在しない |
| 索引の欠落 | `README.md` の一覧と実体のずれ |
| 記録漏れ | 活動ログで頻繁に編集されているのに記録が無いモジュール |
| フォーマットの逸脱 | frontmatter の欠落、命名規則からの逸脱 |

記録漏れの検出には `afterFileEdit` フックが書く活動ログを使います。hooks を無効にしている場合、この項目はスキップされます。

## 使い方

### /review-knowledge から

通常はアクションスキル経由で使います。

```text
/review-knowledge
```

`review-knowledge` スキルが `knowledge-curator` へ走査を委譲し、返ってきたレポートを整理してユーザーに提示します。合意した項目だけを、親エージェントが実際に修正します。

### 直接呼ぶ

```text
knowledge-curator サブエージェントで知識ベースを棚卸しして
```

レポートだけが欲しい場合はこちらが早いです。

### サブエージェントが使えない環境

Claude Code や Codex ではサブエージェントの仕組みが異なります。`review-knowledge` スキルは、委譲できない場合に自分で走査する手順も持っているため、どの環境でも動作します。知識ベースが大きい環境では、カテゴリを分けて複数回に分けることをおすすめします。

## 導入方法

### Cursor Plugin として導入した場合

`agents/` が自動で読み込まれます。設定は不要です。

### init.sh で導入した場合

`.cursor/agents/knowledge-curator.md` に配置されます。不要なら `--no-agents` を付けてください。

```bash
bash skills/project-setup/scripts/init.sh /path/to/project --no-agents
```

## 独自のサブエージェントを追加する

プロジェクト固有の走査が必要になった場合は `.cursor/agents/` に追加できます。ただし追加する前に、スキルで足りないか検討してください。

サブエージェントにする判断基準は次のとおりです。

- 読み込む量が大きく、必要な結論が小さい
- ユーザーとの往復が不要（一度指示すれば完結する）
- 親の会話のコンテキストを消費させたくない

frontmatter で使える主なフィールドは次のとおりです。

| フィールド | 用途 |
|-----------|------|
| `name` | 識別子。ファイル名と一致させる |
| `description` | どんなときに委譲するか。親エージェントはこれを見て判断する |
| `model` | 使用モデル。`inherit` で親と同じ |
| `readonly` | `true` にすると書き込みを禁止する |

`npm run components:check` が `name` とファイル名の一致、`description` の有無、本文の存在を検証します。
